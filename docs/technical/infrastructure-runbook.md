# Service infrastructure runbook

## Source and local verification

Use Node 24 and the pinned pnpm. Run `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm build` and `pnpm test:node:built`. The last command starts an isolated PostgreSQL 17 instance and the built API process, exercises shared-session HTTP auth, CORS/CSRF, raw duplicate headers, writes/replay, MCP bearer access, revocation and outage behavior, then removes its synthetic database. It needs no provider credentials. `pnpm test:postgres` includes SQL, application user isolation, concurrency, rollback, retention, identity and transfer tests.

Build the production image with `docker build -t action-tools:local .`. The non-root image includes Node 24 and PostgreSQL 18 client tools and system CA certificates for the separate backup job. libpq uses `PGSSLROOTCERT=system` with hostname verification; retain the system trust store in the runtime image. CI verifies source and container builds; publishing and deployment require the environment-specific release process below.

## Provider and secret preparation

Prepare separate staging and production environments. In Neon configure a PostgreSQL 18 project in `aws-ap-southeast-1`, a primary read/write endpoint, compute 0.25–1 CU, no production autosuspend, and seven-day restore history. Verify the actual plan supports these values and exposes at least 64 usable server connections. Do not use a transaction-pooling endpoint for the runtime or backup. Create distinct migrator, runtime and export logins. The runtime must neither own tables nor be a superuser nor inherit the export role. The migrator must own application tables and be allowed to grant the required privileges. Keep passwords out of command arguments, tracked files and Terraform variables.

In Gate register the canonical `${PUBLIC_ORIGIN}/mcp` resource and a resource-introspection client `weave-api`; store its secret in the version-pinned `weave-gate-client-secret` Secret Manager secret. Configure that resource's `browser_client_id` to the value used as `GATE_BROWSER_CLIENT_ID`. Register each static SPA as a Gate browser app with a unique `app_id` and only its exact HTTPS `/auth-return.html` URI. Set `GATE_BROWSER_APPS` from those app registrations, `GATE_SESSION_COOKIE_DOMAIN` to the normalized shared DNS parent, and `GATE_BROWSER_SESSION_TTL_SECONDS` within the supported 3600–2592000 second range. Gate's issuer must be an HTTPS subdomain of that parent; API and SPA origins must be under it. Put API/Gate origins, SPA origins, cookie parent, registered app ID and exact return URI in ignored runtime inputs and render them with `pnpm render:runtime-config`. There is no product-specific public Web OAuth client or API login callback. MCP clients register themselves through Gate DCR and use authorization-code PKCE with exact redirects; no manual public client ID or callback registration is required. No feature scopes or signup are provided.

Provision the exact verified GitHub subject (`github:<numeric-id>`) and Gate issuer using `pnpm db:admin map-subject /private/subjects.json` against ADMIN_DATABASE_URL. Each manifest entry contains `{issuer,subject,user}`. `user` must be the existing internal user ID when retaining data; inspect the current mapping before writing. Provision one entry for the verified subject. The command refuses reassignment of an existing subject to a different user. Do not infer identity from email or transfer another user's data. Provisioning is explicit local admission; successful Gate login does not create identity mappings.

These provider settings are operator-managed prerequisites; checked-in Terraform manages GCP resources and does not create Neon projects or Gate registrations. A saved design is not evidence that either provider is configured.

## Administrative commands

Build first. Set `ADMIN_DATABASE_URL` through the process environment and run `pnpm db:admin migrate`. Schema migration is checksummed and serialized; server startup only verifies compatibility. Provision login roles through the provider, then run `pnpm db:admin grant-runtime ROLE` and `pnpm db:admin grant-export ROLE`. The latter creates the non-login `action_export` group and table SELECT grants. Run these operations using the schema-owning migrator identity, never the runtime identity.

Use `pnpm db:admin map-subject PRIVATE_MANIFEST` for an array of `{issuer,subject,user}` records. User reassignment is rejected. Explicitly review manifests; they contain identity information and must stay outside the repository. Runtime reads cannot create subjects.

`pnpm db:admin export PRIVATE_FILE` writes a transaction-consistent PostgreSQL logical transfer plus a SHA-256/count manifest with mode 0600. It requires all-row export privileges. `CONFIRM_WRITE_FENCE=true pnpm db:admin import PRIVATE_FILE` requires an empty target, checks the digest and graph/receipt continuity, and commits all imported rows atomically. Legacy SQL sessions and login attempts are excluded; current browser sessions and login transactions are Gate-owned in Firestore. The transfer uses version 9 with `user_id` columns and rejects other versions. This transfer format is PostgreSQL administrative data; an export from another storage format requires an explicit conversion and decoded-equality rehearsal before use. Never feed a SQL dump to this JSON importer.

`pnpm db:admin snapshot USER PRIVATE_FILE` validates and exports a single decoded snapshot. `CONFIRM_WRITE_FENCE=true pnpm db:admin apply-revocations PRIVATE_MANIFEST` clears inert legacy SQL session/login-attempt rows and disables listed subjects. Gate device sessions and connections are revoked through Gate's management endpoints. Keep the current reviewed subject revocation manifest in separately versioned private storage before applying it; restore operations require this current control record, not a copy from the backup timeline. Rotate `CURSOR_EPOCH` after restoring or cutting over a timeline.

## Release and recovery

### DNS and static hosting

Cloudflare provides authoritative DNS and the SPA through Workers Static Assets. Deploy an assets-only service named `weave-web`, without a Worker script. Gate and the API run on Cloud Run and use standard Cloud Run domain mappings. Create their Cloudflare DNS records from the mapping's returned resource records with proxying disabled. The browser calls the API directly using the shared Gate session and the API's exact-origin credentialed CORS policy.

SPA publication is a mandatory, separate step of every full [normal release](deployment.md#normal-release). The API container serves no SPA files, and neither a successful Cloud Run deployment nor `pnpm build` publishes the Web UI.

1. From the same evaluated source commit as the API image, run `pnpm build` to produce `dist/spa`, then `pnpm render:runtime-config` using the reviewed operator-owned `infra/.local/deployment.json`. The renderer copies the candidate SPA into `.local/spa` and adds its runtime configuration; do not reuse a rendered directory from an earlier build.
2. The renderer replaces `.local/spa` and writes its hosting rules from `spaHostingRules` in `scripts/deployment/runtime-config.mjs`: `_redirects` serves `/index.html` for the root document, and `_headers` sets `Cache-Control: no-store` for `/runtime-config.json`, immutable caching for hashed `/assets/*`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, and framing protection (`X-Frame-Options: DENY` and `frame-ancestors 'none'`, except `SAMEORIGIN` and `'self'` for `/workspace.html`, which the shell frames). Do not replace these files with older operator copies; change the rules in the source instead. In the existing operator-owned static-host configuration, preserve explicit `.html` paths with static asset `htmlHandling: "none"` and point the assets directory at the final `.local/spa`. Deploy those assets to `weave-web`. Keep actual hostnames, account-specific deployment manifests and provider receipts in ignored local settings. Retain the provider deployment version and a SHA-256 manifest of the final published files, including runtime configuration and hosting rules.
3. Retrieve `/`, `/auth-return.html`, `/workspace.html`, `/runtime-config.json` and every referenced asset from the public HTTPS origin. Compare decoded response-body hashes against the candidate manifest (`/` maps to `index.html`) and check cache headers. A 200 response or provider receipt alone does not prove the candidate is serving. If content differs, investigate the serving deployment and CDN cache, correct the mismatch and repeat public retrieval before accepting the release.
4. Verify the exact Gate redirect, authenticated browser session and credentialed API CORS, then exercise the changed UI behavior. For Action text view/edit changes, open an existing Action and verify default View plus Edit/Done transitions. Preserve unsaved proposals. Record source commit, static deployment version, artifact hashes and public content/browser verification separately from API evidence.

Do not mark a full release complete until SPA publication and public content/behavior verification pass. An explicitly scoped API-only release must name the unchanged serving SPA version and source, verify its compatibility with the new API, and state that no UI update was delivered.

Before routing traffic to a changed Gate issuer, verify both API domain certificates, provision that issuer's explicit grants to the existing internal user, and align the GitHub OAuth callback with Gate's canonical origin. A deployed SPA or a pending certificate does not establish successful login. Retain the serving revisions until the fenced identity cutover is ready. Record static asset version, API/Gate image digests, revisions and the actual authentication checks separately.

Follow [deployment](deployment.md) for fenced data cutover, compatible rollout, secret rotation and rollback. Run the migration job from the exact candidate image; inspect its terminal result before updating serving traffic. Pin images by digest and secret values by version. Start with `WRITE_MODE=blocked`, verify actual issuer/resource/user boundaries and read-only clients, then explicitly enable writes after acceptance. Do not infer deployed behavior from local fixtures.

The backup job runs `dist/server/backup.mjs`, takes a PostgreSQL snapshot, streams `pg_dump --format=custom` into private GCS, and uploads its manifest only after the dump and object upload succeed. The separate administrative entry-point check requires explicit export-role membership. Partial objects have no successful manifest and are not restore inputs. Restrict the backup identity to object creation; restoration is a separate privileged operation. A missing success log for 26 hours alerts. Verify actual scheduled backups and rehearse `pg_restore` into an isolated database before production acceptance; JSON administrative transfer tests do not establish custom-format dump restoration or measured RPO/RTO.
